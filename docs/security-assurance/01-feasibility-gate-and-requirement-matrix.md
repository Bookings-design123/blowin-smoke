# Feasibility Gate and Requirement Matrix

**Document role:** SEC-02 controlling capability assessment
**Assessment date:** 2026-08-14
**Implementation authority:** None

## 1. How to read this matrix

Each result applies only to the stated requirement and trust boundary. `PASS` means technically feasible, not implemented, legally approved, or launch-ready. `CONDITIONAL` means every prerequisite is mandatory. `FAIL` is not softened by compensating controls. `BLOCKED` remains blocked until named evidence or authority exists.

Evidence abbreviations:

- **SEC-01:** governing security architecture in `docs/security-architecture/`.
- **NIST-63B:** [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html).
- **RFC-9111:** [HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111).
- **Tor:** [Onion Service protocol overview](https://spec.torproject.org/rend-spec/protocol-overview.html) and [Tor Project operations guidance](https://community.torproject.org/onion-services/).
- **Platform:** the official Apple, Android, Microsoft, W3C, and browser sources cited in the specialized documents.

## 3. Primary SEC-02 question answers (A–AD)

### A–K — E2EE and client architecture

**A. Browser-accessible E2EE:** `CONDITIONAL`. A browser can run a reviewed E2EE client and keep content keys client-side, but the delivered code, endpoint storage, directory, and dependencies remain critical. See F-09–F-11 and document 02.

**B. Plausible mature families:** Matrix's currently maintained Rust-crypto browser stack is an evaluation candidate; MLS (RFC 9420/9750) is a credible protocol family with application work still required; Signal's published designs are a property reference. None is selected.

**C. Unsuitable candidates:** official `libsignal` is unsupported outside Signal and is not a general browser package; legacy `libolm` is deprecated; raw WebCrypto, primitive-only libraries, and ad hoc combinations are insufficient; OpenMLS's browser target remains unsupported/not fully tested in maintainer documentation. See document 02.

**D. Server-blind content:** `CONDITIONAL`; feasible with endpoint-only content keys, authenticated endpoint membership, and no server-readable backup/escrow. The server still sees minimized metadata and can attack web delivery unless separately constrained.

**E. Protocol properties:** adopt a complete supported state machine that supplies authenticated setup, key evolution, forward secrecy, replay/out-of-order behavior, and multi-device semantics. Do not recreate those properties from primitives.

**F. Trusted-device addition:** `PASS` at feasibility level, with signed/interactive approval, anti-replay, contextual confirmation, notification, audit, and revocation.

**G. All devices lost:** account enters a recovery state; old endpoints/sessions are revoked; correspondent identity changes; new endpoints begin without old keys unless a prospective endpoint-controlled recovery mechanism exists.

**H. Recovery separation:** account access can return after evidence-based recovery; inaccessible historical plaintext cannot.

**I. Additional recovery evidence:** an order number is only a pointer. Require a separately issued/saved recovery code or verified bound recovery channel/authenticator; add risk review, delay/notifications, and—only for previously identity-proofed transactions—qualified reproofing. Do not use knowledge questions or order details as sole secrets.

**J. Malicious browser code:** it cannot be eliminated while the service can target and deliver new executable code. Dedicated origin, strict third-party exclusion, release review, CSP/SRI where applicable, transparency/reproducibility, and monitoring reduce risk; a signed native client materially changes the update boundary.

**K. Boundary comparison:** dedicated origin improves isolation; PWA mainly improves installability and update/cache control; signed native materially improves release and key-storage options but increases friction and remains vulnerable at authorized endpoints.

### L–P — Media and capture

**L. Private 4K presentation:** `CONDITIONAL`. Prevent public enumeration and long-lived authorization; use adaptive segmented streaming, protected origin, short session-bound access, no private offline cache, and individualized marks. Authorized capture remains possible.

**M. Capture by client:** browser/PWA prevention `FAIL`; Android native `CONDITIONAL` best-effort; iOS screenshot prevention `FAIL` and recording redaction `CONDITIONAL`; Windows native exclusion `CONDITIONAL`; managed-device restrictions `CONDITIONAL` in controlled deployments.

**N. Impossible protections:** universal screenshot/recording prevention, second-camera prevention, recall of rendered content, guaranteed stripping-resistant watermarking, and guaranteed deletion from uncontrolled endpoints.

**O. Strongest honest anti-leak strategy:** least access + short server authorization + no public enumeration/download UI/private cache + visible individualized session watermark + optional independently tested forensic mark + access/audit/anomaly/revoke + clear handling terms and due process.

**P. Forensic watermarking:** `BLOCKED` pending independent robustness, false-positive, privacy, evidence-chain, and customer-impact validation. It is attribution, never prevention.

### Q–W — Manifest and deletion

**Q. Five-minute visibility:** explicit authenticated reveal atomically sets immutable server timestamps; return an online-only protected projection; deny every later manifest/media/key request at expiry; visibly redact active UI best effort.

**R. Open tab:** active client redacts on a monotonic timer and rechecks on visibility/online events; a frozen/modified/offline client cannot be guaranteed to comply.

**S. Offline:** no offline reveal or manifest cache. If connection is lost after rendering, server enforcement cannot remove pixels; reconnect fails closed after expiry.

**T. Cache/memory/output:** `no-store`, no service worker cache, no prefetch, no plaintext notifications, and no print/download UI reduce exposure. They do not guarantee removal from volatile memory, assistive output, screenshots, print-to-file, devtools, or cameras.

**U. Thirty-minute clock:** server derives it independently from the first reveal event. An idempotent server-accepted initiation before deadline writes an audit receipt even though display access ended.

**V. Deletion guarantees:** only narrowly scoped server/controlled-client lifecycle actions can be verified. External and compromised copies cannot.

**W. Separate lifecycles:** ciphertext, attachments, routing metadata, endpoint keys/state, notification payloads, exports, backups, declassification receipts, canonical quote/order, and required support/audit records each have an owner, class, purpose, hold, and expiry.

### X–AD — Onion, capabilities, minimization, and claims

**X. Onion coexistence:** `CONDITIONAL`; one canonical backend behind an isolated entrance is feasible if route/resource/origin/session/key continuity tests pass.

**Y. Incompatible browser resources:** public third-party analytics/ad pixels, tag managers, chat, CAPTCHA, fonts, maps, media players/CDNs, federated login, error telemetry, payment/age widgets, or clearnet redirects are incompatible by default because they disclose/correlate the Onion visit. Self-host, privacy-proxy under explicit authority, or use a warned transition.

**Z. Safest session relation:** separate cookies/session IDs/CSRF state and explicit reauthentication. Same account authority is acceptable, but signing in creates account correlation. Never pass bearer sessions in URLs.

**AA. Delivery Hub:** immediately exchange the initial narrow capability for a clean-URL session; remove token from logs/referrers/third parties; scope, expire, revoke, rate-limit, and step up every sensitive write.

**AB. Never retain by default:** E2EE plaintext/keys; raw passwords/recovery codes; full payment credentials; raw identity/age evidence; precise GPS outside an authorized active purpose; Delivery Hub/token values; raw proof media; full addresses after justified lifecycle; unrestricted free text; private media URLs/tokens; secrets in logs/analytics; off-duty location; browsing/Onion correlations for advertising; copied phone-call content; unsupported product assertions. Any exception requires recorded purpose/authority/class/retention/access/hold/deletion.

**AC. Potential safe claims:** only after evidence—“End-to-end encrypted wholesale messaging,” “Optional Onion access,” “We minimize the data we collect,” and a narrowly scoped statement that the intermediary cannot decrypt designated message content. Exact conditions are in document 08.

**AD. Prohibited claims:** anonymous order/delivery; Tor makes the transaction anonymous; zero tracking; screenshots/recording impossible or blocked everywhere; media cannot be copied; messages guaranteed gone everywhere; owner/staff can never read any conversation; no metadata; perfect security.

## 4. Overall disposition

The owner intent does not require a technical contradiction to SEC-01. It does require four explicit qualifications:

1. “Strong prevention” of capture becomes layered **deterrence and attribution**, because browser/PWA and second-camera prevention fail.
2. “Disappears” becomes verified access/lifecycle behavior within controlled systems, never guaranteed universal erasure.
3. E2EE applies to conversation content/approved attachments, while catalog media is restricted server-authorized content under the hybrid decision.
4. Account recovery can restore the account; it cannot reconstruct old plaintext when all content keys are lost.

Those are evidence-based boundaries, not reductions in the underlying privacy objective.
