## 1. Evidence method and claim discipline

- A platform or product page was opened and read; search-result snippets are not evidence.
- First-party platform documentation, platform-security material, standards, and official product documentation control. Telegram's official issue tracker is retained only as official product-behavior evidence, not as proof of an operating-system API.
- `WHAT IT ESTABLISHES` is the maximum claim supported by the source. `WHAT IT DOES NOT ESTABLISH` is a mandatory boundary, not a general disclaimer.
- Documentation support is not execution proof. A source can establish that an API exists without establishing that Blowin’ Smoke exercised it, that every OEM or capture tool honors it, or that a complete client satisfies T01–T41.
- Absence of a qualifying public API in the sources reviewed is recorded as `BLOCKED — EVIDENCE NOT ESTABLISHED`; it is not converted into a universal impossibility theorem.
- Undocumented APIs, private framework internals, secure-text-field side effects, implementation accidents, and reverse-engineered third-party behavior cannot satisfy the production gate.
- A screenshot callback after readable pixels were saved and a recording-state callback while readable pixels continue to flow both fail the governing capture requirement.
- External-camera capture remains `NOT PREVENTABLE`. That physical limit does not invalidate successful protection against supported digital capture paths.

### 2.1 Apple evidence disposition

- **Unmanaged iOS/iPadOS arbitrary-UI screenshot veto:** `BLOCKED — EVIDENCE NOT ESTABLISHED`. The opened public sources establish post-capture notification, active-capture state, managed restrictions, and narrow protected-video rendering; none establishes a supported general veto for the complete arbitrary wholesale UI.
- **Unmanaged iOS/iPadOS whole-surface recording exclusion:** `BLOCKED — EVIDENCE NOT ESTABLISHED`. Reactive redaction and narrow protected media are insufficient without exact race, output, and complete-surface proof.
- **`AVSampleBufferDisplayLayer.preventsCapture`:** documentation-supported only for its sample-buffer video layer. Exact platform/version availability, screenshots, ReplayKit, QuickTime, AirPlay, external displays, accessibility, and failure behavior remain `BLOCKED — EXECUTION NOT PERFORMED`.
- **Secure-text-field or private-layer techniques:** `OBSERVED / UNSUPPORTED — NOT ACCEPTABLE FOR PRODUCTION GATE`. Apple documents secure text entry, not screenshot exclusion for arbitrary UI, and requires public APIs used for intended purposes.
- **Unmanaged macOS target-controlled arbitrary-UI exclusion:** `BLOCKED — EVIDENCE NOT ESTABLISHED`. ScreenCaptureKit filters belong to the capturing client; the legacy AppKit sharing constant does not qualify.
- **Managed Apple profile:** documentation-supported as a separate enterprise boundary; enrollment, policy application/removal, fail-closed admission, accessibility, and device execution remain blocked.
- **Apple distribution of the Blowin’ Smoke commerce domain:** the current App Review language is a material product-distribution constraint, separate from platform-security capability. The exact permissible distribution model is `BLOCKED — POLICY / LEGAL DETERMINATION NOT ESTABLISHED`.

### 4.1 Android evidence disposition

- **Primary mechanism:** documentation supports `FLAG_SECURE` for the stated screenshot and non-secure-output paths. All app windows, dialogs, popups, media surfaces, previews, and transitions still require representative proof.
- **Candidate floor:** Android 14 / API 34 is the SEC-03 proof floor, not because the sources prove Android 12/13 incapable, but because Android 11 and below have an explicit reliability warning, Android 14 supplies a current bounded target, and admission must use a currently serviced exact OEM build and patch level. Blanket Android 12/13 admission is `BLOCKED — SUPPORT / EXECUTION EVIDENCE NOT ESTABLISHED`.
- **Callbacks:** screenshot and recording callbacks are detection only; neither satisfies T01–T04 without unreadable capture output.
- **Root/instrumentation:** no source establishes infallible detection. Privileged compromise may bypass controls. The correct response for mandatory missing, stale, revoked, or unacceptable integrity evidence is fail-closed denial, with privacy and false-positive review.
- **Execution:** physical-device/emulator compilation, installation, screenshots, MediaProjection, mirroring, casting, dialogs, Compose, WebView, media surfaces, accessibility, OEM variation, and root/instrumentation tests are `BLOCKED — EXECUTION NOT PERFORMED` in the available environment.
- **Google Play distribution:** current restricted-content policy is a material distribution constraint independent of Android capture capability. Exact permitted private/direct distribution is `BLOCKED — POLICY / LEGAL DETERMINATION NOT ESTABLISHED`.

### 5.1 Windows evidence disposition

- **Primary mechanism:** `WDA_EXCLUDEFROMCAPTURE` is documentation-supported for an app-owned top-level window and a specified set of public capture features. Microsoft's explicit non-DRM/no-strict-guarantee warning controls every claim.
- **Candidate boundary:** the API behavior floor is Windows 10 version 2004. The proposed maintained proof floor is fully patched Windows 11 24H2, with 25H2 or later preferred; this is a support decision, not a claim that earlier builds lack the API.
- **Framework/window topology:** child windows, owned dialogs, popups, embedded browser processes, video swap chains, multiple top-level windows, previews, Remote Desktop, external displays, and graphics-driver variation remain `BLOCKED — EXECUTION NOT PERFORMED`.
- **Capture tools:** Snipping Tool, Print Screen, native recording, Game Bar, Windows.Graphics.Capture, third-party capture, and remote-session outputs remain `BLOCKED — EXECUTION NOT PERFORMED`.
- **Integrity:** MSIX signing, TPM, and managed health attestation are separate evidence layers. None proves display-affinity enforcement or a benign uncompromised runtime.
- **Distribution:** Microsoft Store policy must be reviewed against the final app/catalog/distribution model. That determination is separate from capture capability and remains blocked.

### 6.1 Standards evidence disposition

- **Browser/PWA:** no opened web standard gives a target page authority to exclude itself from normal OS screenshots or recordings. Browser protected-wholesale capture capability remains rejected; public retail and generic onboarding remain unaffected.
- **Resource delivery:** standards support explicit cache policy, token protection, freshness, and replay-aware authorization, but they do not select the future private-media grant format, CDN/origin, key service, watermark pipeline, or revocation architecture.
- **Fail-closed admission:** the standards support binding, freshness, verifier-side validation, and lifecycle discipline. The exact combination of signed build, endpoint key, platform integrity, room/account authorization, and resource grant remains an original design decision; self-asserted `approved=true` or user-agent strings are not evidence.
- **E2EE:** surviving native architectures can support later E2EE evaluation in principle, but SEC-03 does not select Signal, MLS, a library, or a cryptographic profile. Account recovery remains separate from encrypted-history recovery.
- **Accessibility:** anti-extraction controls must not remove required semantic access, navigation, enlargement, captions/transcripts, high contrast, or protected order verification. Representative assistive-technology execution remains blocked.
- **Onion:** public HTTPS remains ordinary retail transport. A public/nonprotected Onion service and approved-client onboarding are separable from a protected native client's transport. Native Onion support is `BLOCKED — SEPARATE AUDITED TRANSPORT NOT SELECTED` and does not by itself block client capture validation.

## 8. Register conclusion

The authoritative evidence supports two serious native control candidates—Android secure windows and Windows display affinity—but no native platform was executed in a representative environment during SEC-03. Managed Apple devices remain a separate enterprise-only documentation candidate. Unmanaged iOS/iPadOS, unmanaged macOS, browsers, and PWAs do not have an established supported whole-surface mechanism that satisfies the current release gate.

Therefore:

- no source in this register creates a `PROVEN CANDIDATE`;
- no source authorizes production implementation or Private Wholesale launch;
- no third-party product behavior is attributed to an operating-system API without platform evidence;
- no undocumented or implementation-accident technique qualifies;
- no missing, unknown, stale, revoked, unsupported, or unproved mandatory state may release protected payload; and
- every remaining execution claim is controlled by the [SEC-03 platform test matrix](sec-03-platform-test-matrix.md), not by documentation alone.
